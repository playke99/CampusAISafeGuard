## 一、模块总览

### 1.1 目录职责

| 文件 | 职责 |

| `events.json` | 事件历史（运行时生成） |
| `snapshots/` | 事件快照图片 |

### 1.2 运行模型

单进程双线程：

```
主线程                        检测线程（daemon）
uvicorn :8200                 VideoCapture -> YOLO -> 状态机 -> 事件
   │                                  │
   └──── /api/state、快照、视频流 ◄────┘（通过 MonitorContext 帧锁共享）
```

### 1.3 数据流

```
本地摄像头 / RTSP / MP4
        │ cap.read()
        ▼
  原始 BGR 帧 ──────────────► 标注帧（ROI + 人框 + 物品框）
        │                              │
        │ 每 detect_interval_sec        └──► MonitorContext.set_frame
        ▼                                        │
 YOLO pose（人+关键点）                            ├─► GET /api/snapshot.jpg
 YOLO detect（物品）                               └─► GET /api/video_feed (MJPEG)
        │
        ▼
 SeatStateMachine.process()
        │ 新事件
        ├─► events.json + snapshots/*.jpg
        └─► Agent 8100（工单/报告/推送）
```

## 二、视频采集流程

### 2.1 视频源解析与打开

`main.py` 的 `open_source()`：

```python
def open_source(source: str):
    if source.isdigit():
        cap = cv2.VideoCapture(int(source))
    else:
        cap = cv2.VideoCapture(source)
    if not cap.isOpened():
        raise RuntimeError(f"视频源打开失败: {source}")
    return cap
```

支持三种来源：

- `"0"`：本机默认摄像头；
- `"rtsp://..."` / `"http..."`：网络摄像头；
- `"*.mp4"`：本地视频文件，用于离线演示。

判断规则在 `detect_loop()` 中：数字或 `rtsp://`/`http` 开头的视为实时流，其余视为文件。

### 2.2 检测主循环

核心步骤（`detect_loop()`）：

1. `cap.read()` 读一帧；失败时区分文件与实时流。
2. 文件源读完后回到第 0 帧循环播放。
3. 实时流失败则释放句柄、等待 5 秒重连。
4. 用 `detect_interval_sec`（默认 1 秒）限制推理频率，降低 CPU/GPU 占用。
5. 调用 `detector.infer(frame)` 得到 `persons` 与 `items`。
6. 调用 `machine.process(frame, persons, items)` 推进状态机，返回新事件。
7. 对新事件逐个 `push_seat_event()` 推 Agent。
8. 生成标注帧并写入共享上下文，供快照与 MJPEG 使用。
9. 循环末尾 `sleep(0.01)` 让出 CPU。

关键代码：

```python
ok, frame = cap.read()
if not ok:
    if is_file:
        cap.set(cv2.CAP_PROP_POS_FRAMES, 0)
        continue
    # 实时流：释放 + 5 秒后重连
...
if now - last_infer >= interval:
    persons, items = ctx.detector.infer(frame)
    events = ctx.machine.process(frame, persons, items)
    for ev in events:
        push_seat_event(ev, agent_url)
    annotated = ctx.detector.annotate(frame, persons, items, rois)
    ctx.set_frame(frame, annotated)
```

### 2.3 帧共享与前端取图

`MonitorContext` 用 `threading.Lock` 保护“原始帧 + 标注帧”：

```python
def set_frame(self, frame, annotated):
    with self._frame_lock:
        self._frame = frame
        self._annotated = annotated

def get_frame(self, annotated=False):
    with self._frame_lock:
        f = self._annotated if annotated else self._frame
        return None if f is None else f.copy()
```

- `GET /api/snapshot.jpg`：取当前标注帧，`cv2.imencode` 成 JPEG。
- `GET /api/video_feed`：循环取帧，按 `multipart/x-mixed-replace` 输出 MJPEG，约 20 FPS（`sleep(0.05)`）。

### 2.4 采集链路的时序与瓶颈

```
cap.read() ──1s节流──► infer（pose + detect）──► process（状态机）──► push Agent（同步，最长 30s）
     │                                                                        │
     └────────────── 标注帧覆盖写入共享上下文 ◄──────────────────────────────┘
```

存在的工程问题：

1. **采集与推理同线程**：推理或推送阻塞时，`cap.read()` 停止，摄像头内部缓冲会堆积，恢复后出现“画面追帧”。
2. **同步推送阻塞**：`push_seat_event()` 使用 `timeout=30` 且在检测线程内调用，Agent 不可用时检测最长停 30 秒。
3. **无采集参数配置**：未设置分辨率、FPS、缓冲大小、编码格式（MJPG），USB 摄像头容易因默认 YUY2 带宽不足导致低帧率。
4. **无健康度指标**：没有采集 FPS、推理耗时、丢帧数、最后帧时间，排障只能看日志。
5. **重连策略固定 5 秒**：摄像头被占用/驱动异常时会无限重试，且没有退避与告警。
6. **读帧不节流**：只限制推理频率，`cap.read()` 仍尽可能快地读，文件源会空转占用 CPU。

## 三、座位目标检测

### 3.1 人体检测（pose 模型）

`Detector.infer()` 对 pose 模型只取 COCO 类别 0（person）：

```python
res = self.pose.predict(frame, conf=self.conf, classes=[0], verbose=False)[0]
kpts = res.keypoints.data.cpu().numpy() if self.pose_mode else None
```

`Person` 保存：

- `bbox = (x1, y1, x2, y2)`；
- `kpts`：17 个关键点，格式 `(x, y, conf)`。

`upper_body_points()` 取索引 `[0, 5, 6, 7, 8]`（鼻、双肩、双肘），置信度 `> 0.3` 才采用；全部缺失时退化为“人体框上部 25% 中心点”。这决定了“人在不在座”的几何判据。

当姿态权重缺失时，当前代码会降级为使用 COCO 检测权重出人框（`pose_mode=False`），此时关键点为空，只能靠人体框估算落点，精度下降但服务可启动。

### 3.2 物品检测（COCO detect 模型）

类别映射固定为：

| COCO id | 名称 | 中文 |
| --- | --- | --- |
| 24 | backpack | 背包 |
| 25 | umbrella | 雨伞 |
| 26 | handbag | 手提包 |
| 28 | suitcase | 箱包 |
| 73 | book | 书本 |
| 41 | cup | 水杯 |
| 39 | bottle | 水瓶 |

检测结果封装为 `Item(bbox, name, conf)`。若检测权重不存在，`items_enabled=False`，物品检测关闭。

### 3.3 ROI 与目标归属

ROI 存储在 `rois.json`，每个座位是一个多边形，坐标归一化到 0~1，因此与视频分辨率解耦：

```json
{"seat_id": "A01", "zone_name": "图书馆自习区A01", "polygon": [[0.1,0.4],[0.3,0.4],[0.3,0.8],[0.1,0.8]]}
```

归属规则：

- **物品归座**：物品框“底边中心”落入哪个 ROI，就算该座位的遗留物；命中第一个 ROI 后 `break`。
- **人归座**：人的上半身关键点（或兜底点）落入 ROI 即算在座；同一人可以同时命中多个相邻 ROI，这是刻意设计，用于“一人占多座”分析。
- **点在多边形内**：`cv2.pointPolygonTest(poly, (x, y), False) >= 0`。

### 3.4 标注与可视化

`Detector.annotate()` 在帧上绘制：

- ROI 多边形与座位号（棕色）；
- 人体框（绿色）；
- 物品框与中文标签（橙色）。

标注帧用于前端视频流与事件快照，不参与识别计算。

### 3.5 检测能力边界

- COCO 的 `book` 类召回率不稳定，桌面书本经常漏检；
- 无法区分“座位上的人”和“路过的人”，只按关键点落点判断；
- 无目标跟踪，无法利用时序 ID 稳定人/物归属；
- 物品归属只看底边中心，重叠座位会误归属；
- 对遮挡、逆光、远距离小目标敏感；
- 没有座位/桌椅专用模型，ROI 完全依赖人工标定。

## 四、占座嫌疑识别逻辑（核心）

### 4.1 状态定义

| 状态 | 含义 | 触发条件 |
| --- | --- | --- |
| `FREE` | 空位 | 无人且无物品（或物品被拿走） |
| `OCCUPIED` | 人在座 | 上半身关键点落入 ROI |
| `AWAY` | 暂离 | 人不在，但缺席时长 ≤ `grace_seconds` |
| `TIMING` | 计时中 | 人不在，宽限期 < 缺席 < 阈值 |
| `SUSPECT` | 疑似占座 | 人不在且缺席 ≥ 阈值，已生成事件 |

### 4.2 单座位运行时字段（`SeatRuntime`）

- `polygon`：座位 ROI；
- `person_miss`：连续未检出人的次数；
- `absent_since`：确认“人不在”的起始时间；
- `items` / `item_since`：当前物品列表与首次出现时间；
- `suspect_event`：当前未处理事件；
- `events_today` / `today`：当日事件计数与跨天重置。

### 4.3 每帧处理流程

`SeatStateMachine.process()` 的执行顺序：

1. 取当前时间、日期、全局阈值、宽限期、确认帧数、是否需要物品。
2. 物品归属：遍历所有物品，按底边中心落入 ROI 分配到 `seat_items[seat_id]`。
3. 逐座位判断：
   - 更新 `items`；首次出现物品记录 `item_since`，物品清空则重置；
   - 用所有行人的上半身点判断 `present`。
4. **有人**：
   - `person_miss=0`、`absent_since=None`；
   - 若之前处于 `AWAY/TIMING/SUSPECT`，记录“人已回座”；
   - 若事件仍为“待处理”，自动关闭为“已自动关闭(人已回座)”；
   - 状态置 `OCCUPIED`。
5. **无人**：
   - `person_miss += 1`；不足 `absent_confirm_frames` 时保持原状态（防抖）；
   - `OCCUPIED` → 有物品（或未要求物品）则 `AWAY`，否则 `FREE`；
   - `FREE` → 有物品（或未要求物品）则开始计时 `TIMING`；
   - `AWAY/TIMING` → 物品被拿走则 `FREE`；否则计算缺席时长：
     - `≤ grace_seconds`：`AWAY`
     - `< 阈值`：`TIMING`
     - `≥ 阈值`：`SUSPECT` 并生成事件
   - `SUSPECT` → 只更新事件的 `absent_minutes`，不重复生成。
6. 跨天：如果 `today` 变化，重置 `events_today`。

### 4.4 判定伪代码

```text
require_items = settings.require_items and detector.items_enabled
threshold = seat_thresholds.get(seat_id, absent_threshold_minutes)

if 有人:
    state = OCCUPIED
elif 连续无人帧数 < absent_confirm_frames:
    保持原状态
elif 无物品 and require_items:
    state = FREE
else:
    absent = now - absent_since
    if absent <= grace_seconds:        state = AWAY
    elif absent < threshold:           state = TIMING
    else:                              state = SUSPECT + 生成事件
```

### 4.5 事件生成细节（`_create_event`）

事件字段：

| 字段 | 说明 |
| --- | --- |
| `event_id` | 12 位随机 ID |
| `event_type` | 固定 `seat_occupation` |
| `camera_id` / `zone_name` / `seat_id` | 位置信息 |
| `occurred_at` | 事件时间 |
| `absent_minutes` | 缺席时长 |
| `items` | 遗留物品 |
| `repeat_count` | 当日第几次 |
| `snapshot` | `snapshots/座位_时分秒.jpg` |
| `item_dwell_minutes` | 物品在座时长（新增） |
| `multi_seat` / `multi_seat_neighbors` | 是否一人多座、邻座列表 |
| `reservation` | 预约在册信息（一卡通后 4 位 + 时段） |
| `status` | 待处理 / 已处理 / 已自动关闭 |

配套逻辑：

- **快照**：保存最近一次参与推理的帧（`_last_frame`），不保存事件瞬间的新帧；
- **一人多座**：计算本座 ROI 中心到其他 `OCCUPIED` 座位中心的距离，小于 `1.5 × 本座 ROI 平均半径` 则视为邻座；
- **预约偏差**：事件时刻查询 `reservation_store.active_for(seat_id)`，有预约但人不在则附加 `reservation`；
- **去重**：`SUSPECT` 期间不重复生成；处置后再次触发则 `repeat_count + 1`；
- **落盘**：`events.json` 每次全量重写，事件按最新在前插入；
- **自动关单**：人回座时若事件仍“待处理”，自动置为已关闭。

### 4.6 设计亮点

1. **连续帧确认**：`absent_confirm_frames=3` 抑制单帧漏检。
2. **状态分层**：暂离 → 计时 → 疑似，避免“一离开就报”。
3. **重复上报抑制**：同一疑似事件只报一次，处置后再犯才累计。
4. **自动关单**：贴条后回座能自动闭环。
5. **一人多座分析**：利用相邻座位空间关系辅助判断。
6. **预约偏差**：把“预约在册但人不在”纳入证据链。
7. **隐私最小化**：预约只保留一卡通后 4 位。
8. **坐标归一化**：ROI 与分辨率解耦，换摄像头不必重标。
9. **在线调参**：阈值、宽限期、确认帧数均可通过 API 修改。
10. **业务闭环**：事件 → 工单 → 推送 Agent → 管理员处置。

### 4.7 判定逻辑的局限

1. **阈值作用在“缺席时长”而非“物品停留时长”**：`item_dwell_minutes` 只做展示，未参与触发。
2. **人物遮挡/弯腰/趴桌**可能导致关键点丢失，误判为离开。
3. **物品短暂被遮挡**会清空 `item_since`，重新出现后从 0 计时。
4. **无目标跟踪**：相邻座位走动、换座会造成状态抖动。
5. **`require_items=False` 时语义退化**：任何离座都会计时，无法区分“空座”和“占座”。
6. **固定阈值不区分时段**：午休、考试周、闭馆前应使用不同策略。
7. **无置信度评分**：只有状态，没有“占座概率”，难以按风险排序。
8. **事件证据单一**：只有一张快照，缺少连续帧/短视频。
9. **预约只做标注不参与判定**：预约超时未到不会单独升级事件。
10. **多座位重叠时归属不确定**：底边中心命中第一个 ROI 即停止。
11. **快照滞后**：保存的是最近推理帧，不一定精确对应事件时刻。
12. **状态机与推送耦合**：推送阻塞会间接影响状态更新。

## 六、现有局限

### 6.1 算法与精度

- 依赖 COCO 通用模型，书本、衣物、水杯等小目标召回不足；
- 无跟踪 ID，换座/遮挡导致状态抖动；
- 只按关键点落点判“在座”，对趴桌、侧身、低头不鲁棒；
- 物品归属只用一个点，重叠 ROI 误归属；
- 无“座位是否被占用”的视觉证据（椅子/桌面状态）；
- 阈值固定，缺少分时段、分区域策略；
- 无占座置信度评分，无法排序处置优先级。

### 6.2 工程质量

- 采集、推理、推送同线程，任一阻塞拖垮整条链路；
- 推送同步 30 秒超时，Agent 故障时检测停摆；
- 无采集参数优化（MJPG、缓冲、分辨率、FPS）；
- 无采集/推理健康指标与告警；
- 事件 JSON 全量重写，数据量大时性能和损坏风险上升；
- 无数据库、无分页查询、无鉴权；
- 日志无轮转，快照无清理策略；
- 前端缺失，演示依赖外部页面。

### 6.3 数据与部署

- 姿态权重路径当前不存在，只能降级检测；
- 无真实场景数据集与微调模型；
- 单摄像头单进程，未考虑多楼层多路视频；
- 无开机自启、进程守护、远程升级；
- 未做隐私合规说明（人脸、画面存储周期）。

### 6.4 产品与运营

- 预约只记录不校验，无法与真实预约系统联动；
- 无工单处置时效、超时升级、统计报表；
- 无“误报反馈”回流机制；
- 无座位热力图、时段分析等管理视图。

## 七、占座监测功能完善开发方案

### 7.1 目标与范围

- 硬件：图书馆现场本地 USB 摄像头（单路起步，预留多路扩展）；
- 识别：稳定判断“座位有人 / 暂离 / 疑似占座”，事件可追溯；
- 展示：一个简易但美观的 Web 结果页（实时座位图 + 事件列表 + 详情）；
- 运维：开机自启、断流重连、日志与健康检查；
- 边界：不做人脸识别，不采集学生身份，只做座位与物品状态。

### 7.3 硬件与安装

- 摄像头：1080P USB 摄像头，优先支持 MJPG 免驱；
- 镜头：2.8~4mm，覆盖 4~8 个座位；
- 安装高度：2.2~2.8 米，俯角 30°~45°，避免正对窗户逆光；
- 补光：均匀漫射光，避免灯光直射镜头；
- 布线：USB 3.0 接口，线长超过 3 米加有源延长线；
- 隐私：镜头只覆盖座位区域，页面不展示可识别人脸的高清原图（可打码或只给座位区域）。

### 7.4 采集优化设计

1. **独立采集线程**：只做 `cap.read()`，写入“最新帧邮箱”，永不阻塞。
2. **参数设置**：

```python
cap = cv2.VideoCapture(index, cv2.CAP_DSHOW)   # Windows
cap.set(cv2.CAP_PROP_FRAME_WIDTH, 1280)
cap.set(cv2.CAP_PROP_FRAME_HEIGHT, 720)
cap.set(cv2.CAP_PROP_FPS, 25)
cap.set(cv2.CAP_PROP_FOURCC, cv2.VideoWriter_fourcc(*"MJPG"))
cap.set(cv2.CAP_PROP_BUFFERSIZE, 1)
```

3. **推理降频**：占座判定不需要高帧率，1~2 FPS 足够；用“最新帧”而非队列，避免延迟累积。
4. **断流重连**：指数退避（1s/2s/5s/10s/30s），连续失败写入健康状态并在页面提示。
5. **看门狗**：超过 `N` 秒没有新帧，重启采集线程并记录日志。
6. **健康指标**：采集 FPS、推理耗时、丢帧数、最后帧时间、重连次数，暴露 `/api/health`。
7. **优雅退出**：`SIGINT` 释放摄像头、关闭数据库、停止线程。

### 7.5 识别算法升级

#### 阶段一：稳定基线（优先）

- 人体：YOLO pose（yolo11n-pose / yolo26n-pose），保留关键点；
- 物品：训练专用小模型，类别建议：
  `person, chair, desk, backpack, book, cup, bottle, laptop, clothes, umbrella`；
- 数据：每个类别 500~1000 张现场图，Label Studio/Roboflow 标注，YOLO 格式；
- 训练：YOLO11n/s，输入 640，按现场光照做数据增强；
- 推理：人体与物品可分两个模型，也可合并为一个多类模型。

#### 阶段二：时序稳定

- 引入跟踪（ByteTrack / BoT-SORT），给人/物分配 `track_id`；
- 人的座位归属用“关键点 + 人体框底边中心”双判据，连续 K 帧投票；
- 物品归属用“底边中心 + 与座位中心距离 + IoU”综合评分；
- 连续 N 帧命中才切换状态，连续 M 帧丢失才认为离开（双阈值防抖）；
- 事件证据：事件前 3 帧 + 事件帧 + 事件后 3 帧，或 10 秒短视频。

#### 阶段三：判定策略

- 区分两个时长：
  - `item_dwell_minutes`：物品在座时长；
  - `unattended_minutes`：物品在座且人不在的时长（触发主依据）。
- 分时段阈值：开馆、午休、闭馆前分别配置；
- 分区域阈值：热门区更严格，靠窗区更宽松；
- 占座置信度：综合缺席时长、物品数量、邻座占用、预约状态打分；
- 预约联动：预约时段开始后 `X` 分钟未到，单独生成“预约爽约”事件；
- 误报反馈：管理员标记误报后，自动记录并支持后续规则/模型迭代。

### 7.6 状态机与业务规则

- 状态保持 5 态，但增加：
  - `confidence`（0~1）；
  - `last_seen_at`、`last_item_at`；
  - `track_ids`、`evidence`（快照列表）。
- 事件生命周期：
  `待处理 → 已贴条 / 已清座 / 误报 / 已自动关闭`。
- 冷却时间：同座位处置后 `cooldown_minutes` 内不重复报。
- 升级规则：当天第 2 次自动升级为高优先级并通知值班负责人。
- 自动关闭：人回座且物品仍在 → 自动关闭；物品被清走 → 自动关闭。
- 闭馆清理：闭馆后统一生成“遗留物品”清单。

## 八、常见 Bug 与排查思路

### 8.1 摄像头采集

| 现象 | 可能原因 | 排查方法 | 处理 |
| --- | --- | --- | --- |
| `视频源打开失败: 0` | 索引错误 / 被其他程序占用 / 无权限 | 用相机应用确认设备；换索引 1、2 试 | 关闭占用程序；改用 `CAP_DSHOW`；确认隐私权限 |
| 画面全黑 | 首帧未就绪 / 曝光未稳定 / 镜头盖 | 连续读 10 帧丢弃前几帧；看曝光 | 预热 1~2 秒；检查镜头盖与补光 |
| 绿屏/花屏 | 编码或带宽不足（YUY2） | 查看分辨率与 FPS 是否达标 | 设置 MJPG、降低分辨率、换 USB3 口 |
| 帧率很低（5 FPS） | USB2 带宽 / 高分辨率 / 自动曝光 | 打印 `CAP_PROP_FPS` 与实测帧数 | 720P + MJPG；换 USB3；关闭自动曝光 |
| 画面延迟 3~5 秒 | 缓冲区堆积 / 读帧太慢 | 对比 `cap.read()` 与推理耗时 | `BUFFERSIZE=1`；采集与推理分离；只保留最新帧 |
| 运行一段时间卡死 | 驱动异常 / USB 掉线 | 看最后帧时间与系统事件 | 看门狗重启采集；指数退避重连 |
| 断流后不恢复 | 重连逻辑只 catch 打开异常 | 查看重连日志 | 重连失败也要记录；增加最大重试与告警 |
| 摄像头索引变化 | 多 USB 设备枚举顺序变化 | `cv2.VideoCapture(i)` 逐个试 | 用设备名称/序列号绑定，或固定 USB 口 |
| 分辨率与标定不一致 | ROI 归一化但画面被拉伸 | 对比实际帧尺寸 | 固定采集分辨率；ROI 用归一化坐标 |
| 逆光/过曝 | 摄像头正对窗户 | 查看直方图 | 调整安装角度；开启宽动态；补光 |
| MP4 演示循环闪烁 | 循环回到第 0 帧 | 观察时间戳 | 循环前清空状态机或用长视频 |

### 8.2 识别模块

| 现象 | 可能原因 | 排查方法 | 处理 |
| --- | --- | --- | --- |
| 启动报权重不存在 | 路径错误 / 文件未拷贝 | 打印解析后的绝对路径 | 修正 `settings.json`；或用降级检测 |
| `ultralytics` 导入失败 | 环境不对 / 版本冲突 | `pip show ultralytics` | 在专用 conda 环境安装 |
| CUDA 报错 | 驱动/版本不匹配 | `torch.cuda.is_available()` | 改用 CPU 或重装匹配版本 |
| 推理很慢（>500ms） | CPU 推理 / 分辨率过大 | 记录 `infer` 耗时 | GPU；降分辨率；换 n 模型；降频 |
| 检测不到人 | 类别过滤错 / 置信度太高 | 打印原始 `boxes` | 确认 `classes=[0]`；降低 `conf` |
| 关键点为空 | 用了检测模型而非 pose | 打印 `res.keypoints` | 加载 pose 权重；降级时接受精度损失 |
| 物品全漏检 | COCO 类别不匹配 / 小目标 | 打印物品类别与置信度 | 训练专用物品模型；提高分辨率；裁剪 ROI 推理 |
| ROI 错位 | 分辨率变化 / 坐标未归一化 | 叠加 ROI 到当前帧 | 统一采集分辨率；使用归一化坐标 |
| 一人被判多座 | 关键点跨 ROI | 看标注帧 | 增加座位中心距离约束；跟踪 ID 绑定 |
| 状态频繁抖动 | 漏检/遮挡 | 看 `person_miss` 与状态日志 | 提高确认帧数；引入跟踪与双阈值 |
| 一直不生成事件 | 阈值太大 / 物品要求未满足 | 看状态是否到 `SUSPECT` | 调低阈值；检查 `require_items` 与 `items_enabled` |
| 事件重复上报 | 处置后状态未清零 | 查看事件与状态机 | 检查 `resolve_event` 与冷却时间 |
| 快照保存失败 | 目录权限 / 磁盘满 | 看 warning 日志 | 创建目录；清理磁盘；改用相对路径 |
| 推送失败但检测正常 | Agent 未启动 / 端口错误 | `curl http://127.0.0.1:8100/health` | 启动 Agent；改为异步推送 |
| 前端取不到画面 | CORS / 端口 / 流被占用 | 浏览器 Network 面板 | 开启 CORS；确认 8200；避免多标签同时拉流 |
| MJPEG 卡顿 | 编码耗时 / 网络 | 看 CPU 与帧间隔 | 降分辨率/帧率；改用 WebSocket 或 HLS |

### 8.3 五步定位法

1. **看画面**：`/api/snapshot.jpg` 是否有图、ROI 是否对齐；

5. **看下游**：`/api/workorders` 与 Agent 日志是否收到。
