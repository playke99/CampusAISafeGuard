## 第一章 设计必要性与方案比选

> 评估对象：数智卫校 · 校园安全 AI 预警与干预系统  
> 评估日期：2026-11-12 · 评估结论：**当前阶段不启动独立的正式数据库设计工程，继续沿用并规范维护现有轻量数据库方案**

### 1. 现状盘点

系统已完成并落地一套轻量数据库设计，而非"无数据库设计"状态：

| 项 | 现状 |
| --- | --- |
| 数据库 | SQLite（WAL 模式），零部署嵌入式 |
| 结构定义 | [server/sql/schema.sql](../server/sql/schema.sql)，10 张表 + 11 个索引 |
| 数据访问层 | [server/core/db.py](../server/core/db.py)，统一连接、建表、种子、写入 |
| 实体覆盖 | 10 张业务表：users / sessions / alerts / interventions / events / work_orders / violations / push_records / devices / audit_logs（覆盖用户/会话、预警、干预、事件、工单、违规、推送、设备、审计） |
| 关联方式 | `alerts.event_id` ↔ `events.event_id` ↔ 工单/违规/推送，一事一档可双向追溯 |
| 运行方式 | 单进程读写，测试全程覆盖（78 项通过） |

### 2. 评估维度分析

#### 2.1 业务需求

| 需求 | 强度 | 现有方案满足度 |
| --- | --- | --- |
| 预警闭环留痕（受理/干预/闭环） | 高 | 满足：`alerts` + `interventions` 状态机完整 |
| 一事一档追溯 | 高 | 满足：`event_id` 贯穿六类记录 |
| 分级推送与工单 | 中 | 满足：`push_records`、`work_orders` |
| 权限与审计 | 高 | 满足：`users`/`sessions`/`audit_logs` |
| 趋势统计 | 中 | 满足：24 小时趋势、级别/类型分布为简单聚合查询 |
| 多校区级联 / BI 分析 / 大屏 | 当前无 | 触发时再评估 |

#### 2.2 功能迭代规划

- 近期迭代集中在**算法增强与接入扩展**（实时视频流、ASR/LLM 增强、更多区域配置），
  均为计算侧工作，不引入新的实体关系；
- 已规划的演进（移动端、教育局对接）属于接口扩展，可在现有 `events` 表上扩展
  `event_type`，无需结构性重构。

#### 2.3 数据存储量级预估

按一所万人规模中职/高职学校估算：

| 表 | 日增量估算 | 年增量估算 | 说明 |
| --- | --- | --- | --- |
| alerts | 20–100 条 | ≤ 4 万条 | 含去重后真实预警 |
| events | 30–150 条 | ≤ 6 万条 | 含工单/违规/报告 |
| interventions | 40–200 条 | ≤ 8 万条 | 每条预警平均 2 次干预 |
| audit_logs | 200–1000 条 | ≤ 40 万条 | 操作日志，体量最大 |
| push_records / violations | ≤ 100 条 | ≤ 4 万条 | — |

**年总数据量 < 60 万行，体积 < 200 MB**。SQLite 在此量级下查询性能充足（已有索引覆盖
status/severity/time/event_id 等全部高频过滤字段），远未触及需要分布式或独立数据库服务的门槛。

#### 2.4 数据关联复杂度

```text
users ──< sessions
users ──< audit_logs
devices ──< alerts (camera_id)
alerts ──< interventions
alerts >── events (event_id 1:1)
events ──0..1 work_orders
events ──0..1 violations
events ──0..n push_records
```

- 实体 9 个、关系 8 条，均为一对多/一对一，无多对多、无递归层级；
- 复杂度为**低-中**，现有扁平结构 + `event_id` 关联即可表达，无需引入ORM 建模工程。

#### 2.5 并发与可用性

- 使用场景：值班室 2–5 人同时在线，并发请求 < 10 QPS；
- SQLite WAL 模式支持单写多读，实测测试全程无锁等待问题；
- 单点部署符合学校当前"保卫处单机 + 局域网访问"的部署形态。

### 3. 评估结论

| 维度 | 评分 | 说明 |
| --- | --- | --- |
| 业务需求复杂度 | 低-中 | 闭环留痕已被现有设计完整覆盖 |
| 数据量级 | 低 | 年 < 60 万行 / < 200 MB |
| 关联复杂度 | 低 | 9 实体 8 关系，无多对多 |
| 并发压力 | 低 | < 10 QPS，单写多读 |
| 演进不确定性 | 中 | 多校区/级联为远期可能 |

**结论：暂不启动独立的正式数据库设计工程。**  
现有 `schema.sql` 即为当前阶段的正式数据模型设计产物，按第 4 节规范维护即可；
当第 6 节任一触发条件达成时，再启动正式设计（届时按第 5 节清单执行）。

### 4. 现阶段的轻量数据存储规范（替代方案）

1. **结构变更唯一入口**：所有表结构变更只改 `server/sql/schema.sql`，
   禁止在代码中零散执行 DDL；新增字段必须带默认值保证旧库兼容；
2. **写入唯一入口**：业务写库统一走 `server/core/db.py` 的 `save_*` 函数，
   禁止在 API 层直接拼 SQL（查询除外，查询必须参数化）；
3. **时间规范**：统一 Unix 时间戳（REAL，秒），展示层格式化；
4. **编号规范**：`ALM-YYYYMMDD-xxxxxxxx`（预警）、`EVT-YYYYMMDD-xxxxxxxx`（事件），
   由 `ai/alert_engine.py` 统一生成；
5. **索引纪律**：新增高频过滤字段时同步在 `schema.sql` 补索引，并在测试中验证；
6. **归档策略**：`archive/*.jsonl` 作为冷数据落盘；生产环境每月归档清理一次
   `audit_logs` 中 90 天前的记录（导出 JSONL 后删除）；
7. **备份策略**：每日备份 `data/campus_security.db`（含 WAL 文件），保留 30 天；
8. **迁移预案**：`schema.sql` 与查询均保持 ANSI SQL 子集，可平移 MySQL/PostgreSQL，
   迁移步骤见 docs/01_系统总体方案.md 第七章。

### 5. 正式数据库设计启动预案（触发后执行）

#### 5.1 前置调研清单

- [ ] 部署形态确认：单校区 / 多校区集中 / 教育局级联
- [ ] 数据量级实测：连续 30 天各表日增量采样
- [ ] 并发实测：高峰时段在线人数与 QPS
- [ ] 数据保留策略：监控证据留存期限（合规要求）
- [ ] 对接系统清单：学工系统、一卡通、人脸库、教育局平台的字段映射
- [ ] 权限模型复核：是否需要院系级数据隔离（行级权限）
- [ ] 容灾要求：RPO / RTO 指标
- [ ] 现有数据迁移量与停机窗口

#### 5.2 表结构设计规范（届时执行）

- 命名：小写蛇形复数（`alerts`），关联字段 `<表名单数>_id`；
- 主键：统一 `BIGINT` 自增代理键 + 业务唯一键（`alert_id` 等）唯一约束；
- 时间：创建/更新时间字段成对出现（`created_at`/`updated_at`），数据库时区 UTC；
- 枚举：状态/级别/类型使用短字符串 + 检查约束（CHECK），不散落魔法值；
- 金额/比率：禁用 FLOAT，使用 DECIMAL；
- 软删除：业务表统一 `deleted_at`（审计要求）；
- 大字段：`evidence`/`detail` 等 JSON 字段使用 JSON 类型（PostgreSQL JSONB）。

#### 5.3 字段约束规则

- 非空：业务必填字段 NOT NULL + 默认值；
- 唯一：业务编号、用户名、设备编号 UNIQUE；
- 外键：`event_id` 关联加外键（PostgreSQL）或应用层一致性校验（高并发写入时）；
- 长度：字符串字段显式 VARCHAR(n)，禁止无界 TEXT 滥用。

#### 5.4 索引优化方案

- 覆盖现有高频查询：`status+severity+occurred_at` 复合索引（预警列表）、
  `event_id`（追溯）、`created_at`（时间范围）；
- 审计表按月份分区（PostgreSQL 声明式分区）；
- 慢查询纪律：任何 > 100ms 的查询必须进 `EXPLAIN` 评审；
- 禁止在 WHERE 中对索引列做函数运算。

#### 5.5 ER 关系图产出要求

- 工具：Mermaid `erDiagram`（可入文档版本控制）；
- 覆盖：全部实体、主外键、基数（1:1 / 1:n / n:m）、关键字段；
- 粒度：核心域（预警闭环）单独一张详图，支撑域（用户/设备/审计）一张简图；
- 评审：与后端、前端、校方信息中心三方评审通过后冻结版本。

### 6. 触发条件（任一达成即启动正式设计）

| 触发条件 | 阈值 |
| --- | --- |
| 部署形态变化 | 多校区集中部署或对接教育局平台 |
| 数据量 | 单表年增量 > 100 万行，或库文件 > 5 GB |
| 并发 | 在线用户 > 50 或峰值 > 50 QPS |
| 分析需求 | 需要跨学期/跨校区的 BI 报表或数据大屏 |
| 合规要求 | 监管要求独立审计库或行级权限隔离 |

### 7. 后续执行步骤

1. 维持现有 SQLite 方案，按第 4 节规范维护；
2. 每月抽样检查各表行数与慢查询（指标页可观测，见 docs/01_系统总体方案.md 第七章）；
3. 触发条件达成时，按第 5 节预案启动正式设计，产出物包括：
   调研报告、逻辑模型（ER 图）、物理模型（DDL）、迁移脚本、评审记录；
4. 正式设计通过评审前，现有系统继续以 SQLite 运行，不做并行改造。
